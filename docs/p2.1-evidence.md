# P2.1 evidence - one-use grants and RS256 module access

Date: 2026-09-29. P2.1 only; module app migrations, Core refresh sessions and reward events remain later phases.

## Guard-first implementation

Extended G1 and created the named G2 before boundary implementation. The initial run had 21 passes and 2 failures: G1 received HTML from the missing grant route; G2 got 404 instead of 401 at exchange. Final G1/G2 covers 32 cases: current membership, subject/Hub binding, disabled/unassigned identities, wrong/rotated/disabled service keys, grant/state hashing, expiry/state/replay/concurrency, wrong audience/issuer/key/algorithm, HS Core JWT rejection, required bounded claims, unsafe key URLs, return-path allowlists, callback Origin/state, mutation CSRF, cookie flags, configuration and rate limits. No extra automated suite was added.

## Isolated manual checks

Used a disposable MongoDB 7.0.14 replica set via the existing temporary mongodb-memory-server installation outside repository dependencies. Ephemeral RSA/service credentials were generated only inside the fixture process. A synthetic handoff@p21.example.test user and Plum College were isolated in collegehubs_demo_p21. No production DB or real college activation was used.

- Real MongoDB concurrent exchange: one 200, one 409; retained access JTI, bounded access expiry and exactly 30 days of binding retention.
- Local gateway localhost:5180 served Core and a disposable in-memory Arcade callback/session stub. Core sign-in happened once. Arcade was enabled only in this fixture; Interview/Learn stayed unavailable.
- Browser followed the full-document Arcade link, received browser state, submitted the native Core form and landed at clean /arcade after the callback's server exchange/local RS256 verification/session creation. The page showed the expected fixture username/college without a second login.
- Verified callback cookie Secure, HttpOnly, SameSite=Lax, Path=/arcade; callback response 303 Location=/arcade.
- Module session projection had only userId, hubId, username, theme, expiresAt, csrfToken. No JWT or service/private key was returned to the browser.
- Missing CSRF deletion: 403. Valid module logout: 204. Session read after logout: 401. Consumed callback state replay: 403 (Core grant replay is separately 409).
- Built JS/HTML scan found zero private PEM markers, CORE_MODULE_PRIVATE_KEY, CORE_SERVICE_KEY or fixture service-key prefix.
- Request diagnostics used method/path/status, field names and cookie-presence boolean only, never credentials or form values.

The browser check exposed a real integration issue: no-referrer makes the Origin of a native form POST null. Core uses strict-origin to preserve exact-Origin checks while keeping paths/query values out of Referer. Origin/state checks were not relaxed. This behavior was verified against the [WHATWG Fetch Standard](https://fetch.spec.whatwg.org/#append-a-request-origin-header).

## Delivered and limits

Core models/indexes, hashed issuance/atomic exchange, 30-day bindings, bounded config, server-only stdin credential provisioning, shared schema/pure Node verifier/state/CSRF/cookie helpers, and gated form navigation are implemented. READMEs, env names and the detailed handoff contract are updated. Reset deletes disposable module grants but preserves operator service credentials.

Production keys, actual module callback/session stores and gateway deployment remain operator/module-phase work. Modules stay disabled by default. Already-issued module sessions can remain valid for at most 15 minutes after Core logout or membership change. No new dependencies or imported module edits were made. Existing lockfile changes and untracked input documents remain excluded.
