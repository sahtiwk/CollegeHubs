# P1.1 verification - 2026-09-29

## Scope and registry status

P1.1 implements registry-driven single-Hub identity, transactional provisioning, optional OAuth passwords, scoped Core tokens, current membership helpers, /me and assignment retry. Minimal tenant filters and onboarding UI compatibility were necessary to avoid exposing foreign data while introducing the identity boundary. P1.2 still owns pagination, full AuthProvider/HubThemeProvider, theme loading and mobile shell. Socket and module surfaces do not exist yet; G1 does not claim their future coverage.

The request to confirm a real college/domain received no domain value. The supplied `cvr.ac.in` reference therefore remains **draft**, with no confirmation evidence. No real institution is active by default. Synthetic active colleges were created only in an isolated temporary local database, never in the shipped registry or configured database.

## Automated G1, written first

Command: `node --test tests/guards/hub-isolation.test.js` (or `npm run test:guards` from server).

The first assertion was added before boundary changes and failed with leaderboard HTTP 200 instead of expected 401. The completed guard passes 15 checks using isolated model fixtures and actual Express routes:

- Anonymous tenant reads denied.
- Foreign/missing-Hub posts, profiles, likes and rankings hidden.
- Unknown/legacy identities limited to self/onboarding access.
- Self DTO and own mutation ownership retained; other same-Hub profile writes denied.
- Browser-supplied Hub, college, verification, identity and reward fields cannot change access.
- Current disabled membership/Hub/college and stale membership tokens rejected.
- Display labels/theme values cannot change access; empty scope cannot match missing-Hub data.
- Exact IDNA normalization rejects suffix lookalikes, implicit subdomain matching and URL delimiters.
- Active registry entries require domain evidence and reject duplicate domains and unsafe themes.
- OAuth-only identity has no required password; password identities still require one.
- Invalid Google issuer/audience/expiry/verified-email/subject cannot reach assignment.

The domain guard found that Node's domainToASCII can interpret URL delimiters. Input delimiter rejection was added and the same guard then passed. No parallel test suite or non-guard automation was added.

## Manual real MongoDB verification

A one-node MongoDB 7.0.14 replica set was started locally with an isolated temporary data directory. The fixture launcher was installed under the OS temporary directory, outside repository packages; existing lockfiles were preserved. Docker was unavailable, so no container or existing DB was used. Google verification responses were fixtures; no provider calls or real Google credentials were used.

| Operation | Observed final result |
|---|---|
| Three simultaneous password registrations for one synthetic active domain | All 201 and assigned the same Hub |
| DB count after concurrency | Exactly 1 Hub, 4 Channels |
| Repeated ensureHubForCollege | Still 1 Hub, 4 Channels |
| Password `/me` | membershipVerified=false; verificationMethod=domain-claim |
| Trusted hosted-domain Google `/me` | membershipVerified=true; verificationMethod=google |
| Google user storage | googleSubject stored; no password |
| Repeated same Google subject | Same account, no email-only merge |
| Unknown password/Google domains | hubId=null, onboarding-only scope, explicit unassigned response |
| Retry for unknown domain | Still unassigned, no catch-all Hub |
| Google email collision with password user | 409 |
| Browser-forged Hub/college/verification registration payload | Unknown domain remained unassigned |
| Injected failure on second Channel upsert | Account persisted as pending; no Hub, orphan Channel or user assignment committed |
| Retry after restoring Channel writes | Assigned; exactly 1 Hub and 4 Channels |
| Duplicate active domain mapping | MongoDB unique-index error 11000 |
| Real scoped feed with A, B and legacy posts | Only A's post returned to A |

| Seed hook twice on a separate fixture connection | Exactly 1 College, 1 Hub, 4 Channels |

The initial transaction run exposed a Hub validator using document context during a query upsert. It was fixed to read the upsert ID, and the concurrency/rollback/retry checks above were rerun successfully. Transactions were real MongoDB transactions; only the deliberate failure and Google identity response were stubbed.

## Compilation and review

Root Vite production build and backend syntax checks pass. Existing Vite/PostCSS/Browserslist warnings remain outside this phase. Root and server lockfile SHA-256 hashes match the start of the task. No configured real database, imported module files, remote Git branch or deployment was modified.

Google ID-token verification uses the installed library's signature/issuer/audience/expiry checks and Core's explicit claim checks. Google documents that a third-party non-Gmail email without hosted-domain evidence can have stale email_verified claims; those accounts remain unverified domain claims in this implementation. See [Google ID-token verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token). Transactions follow [Mongoose's transaction interface](https://mongoosejs.com/docs/transactions.html); no dependency version changes were needed.
