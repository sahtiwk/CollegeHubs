# P2.2 evidence: idempotent Aura receipts and pending recovery

Completed the P2.2 ledger/contract scope only. Scoring is inactive in normal startup; fixture rules verify the skeleton until P6 production activation. Real module pending/read/reconcile adapters remain in P7/P8/P9. No scheduler/outbox, live provider, second module login, new UI or palette change was introduced.

## Guard-first implementation

Extended G1 and added G3 before implementing the event boundary. The first run recorded 22 passes and two failures: missing endpoint returned 404 instead of 401 in G3, and G1 received HTML from that same missing endpoint. Only the approved named guard suites were changed.

Final full G1/G2/G3 execution: **45 checks passed, zero failures, zero skips**, including the transaction-group parent. G3 ran against an isolated MongoDB 7.0.14 replica set, using the already-present temporary mongodb-memory-server installation outside this repository. No dependencies or lockfiles were changed. The guard creates and drops only its randomly named disposable local database; it never loads app .env or uses live providers.

Covered service-only ingestion; Core JWT/browser/source/type rejection; current user/Hub/college/membership-version checks; retained JTI/subject/Hub binding and occurrence lifetime; concurrent identical delivery; payload conflicts; semantic aliases and alias conflict; exact type/game caps; partial source budget; global user-day deduplication; immutable terminal zero receipts; separated external replacement; old/future/malformed/private-content rejection; transaction rollback; response errors, oversize limits and Retry-After.

## Manual persisted stub recovery

Used separate disposable databases `collegehubs_demo_p22_manual` (Core) and `collegehubs_demo_p22_stub` (stub result) on an isolated replica set. Synthetic p22.example.test identity, ephemeral service credential and retained issuance were confined to the process. A result and its frozen pending event were committed together before network delivery. No real domain was activated and no real module backend was claimed complete.

Observed console walkthrough:

```text
Normal startup: 503 AURA_RULES_INACTIVE, retryable true
Core stopped, reload: result outcome success, event pending, attempts 2
Presentation state: Saved; Aura pending
Restore Core with fixture rules; discard first response: 201
Stored local status remains pending
Owned-read/manual replay: 200 duplicate, exact original receipt, award 5
Persist acknowledgement: delivered
Core canonical ledger rows: 1; engagement: 5
Second same-game result: 201, award 0, reason daily_fact_limit
Core readiness after recovery: 200
```

This is a manual backend stub demonstration of the recovery contract, not released module UI. Its bounded failed calls used a two-second AbortSignal with one retry. The contract specifies module-owned result-read authorization, durable acknowledgement/CAS, service-only pages of at most 50, bounded manual reconciliation, permanent-error attention and no automatic-delivery SLA. Those adapters will be implemented with their real domain models in their named phases.
