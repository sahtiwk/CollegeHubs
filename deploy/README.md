# Free staging deployment

Status: P11.1 deployed password-login MVP verified on 2026-10-10: four Render Free APIs, Pages frontend/gateway, Atlas and Neon. See [dated deployment evidence](../docs/p11.1-evidence.md) and [P11.2 release verification](../docs/release-evidence.md). Use free provider hostnames; cvr.ac.in is the membership domain, not an assumed custom hosting domain. The steps below are a setup runbook, not instructions to recreate existing services.

1. Sign into Cloudflare Pages, Render, Atlas and Neon with your own accounts/MFA. Select Free, without paid upgrades. Connect this repository when ready to publish. No friend's deployment or credentials are needed.
2. Atlas: use a Free cluster with three separate logical databases and three database users, each restricted to its own database (Core, Arcade, Interview). Use TLS and restrict network access to service outbound ranges. Neon: create a Free project and a fresh database named `collegehubs_demo_learn_staging`, with Learn-only credentials. Do not use Render's expiring free PostgreSQL for retained data.
3. Create a Pages project to get its assigned HTTPS origin. Set **root directory `apps/web`**, Node `24.12.0`, build command `cd ../.. && npm ci --include=dev && npm run build:web`, output `dist` relative to that root. Functions are under `apps/web/functions`; the build uses the root workspace lock. Add `CORE_API_ORIGIN`, `LEARN_API_ORIGIN`, `ARCADE_API_ORIGIN` and `INTERVIEW_API_ORIGIN` when Render assigns them. `_routes.json` excludes UI/assets from Functions. No top-level 404 page or custom college domain is needed.
4. Import root `render.yaml`. It defines four Free web services, independent filters, no disks/databases/workers/cron/paid previews. Keep repo-root build context. Builds install only the selected service and contracts. Learn compiles TypeScript then prunes build dependencies.
5. Fill the provider settings from each service's `.env`. Core `APP_ORIGIN`/`ALLOWED_ORIGINS` and Learn `APP_ORIGIN` must equal the Pages HTTPS origin. Learn `CORE_API_BASE_URL` is Core's public HTTPS origin. Generate a local RSA keypair of at least 2048 bits. Core gets the private key, JWT secret, Mongo URI and public-key JSON map. Learn gets only the matching public key/key ID, its own service key and PostgreSQL URI. Keep keys in ignored local files/provider settings, never frontend variables.
6. Run `node deploy/prepare-staging-keys.mjs` to generate separate staging credentials in ignored `.local/staging/credentials.json`; reruns preserve existing keys. With the explicitly selected Core `MONGO_URI`, run `npm run provision:hubs -w @collegehubs/core`; repeats preserve one CVR Hub/four channels. Feed each `provisioning` object from the local bundle on stdin to `services/core/scripts/provisionModuleService.js`. Learn requires `learn.quiz_completed` and `learn.node_mastered`, Arcade requires `arcade.game_completed`, and Interview requires `interview.completed`. Core stores only each key's hash; put the original in the corresponding module's `CORE_SERVICE_KEY`. No paid remote shell is needed.
7. For the empty Learn demo DB, locally set `DATABASE_URL`, `DEMO_RESET_ENABLED=true`, `DEMO_DB_NAME_ALLOWLIST=collegehubs_demo_learn_staging`, with `NODE_ENV` unset/development. Run `node services/learn/scripts/setup_demo.ts --confirm=collegehubs_demo_learn_staging --disposable-data-only`. It refuses existing tables and never drops them. Remove reset settings afterwards. This is not a production migration command.
8. Deploy Core, then Learn, Arcade and Interview independently and verify each `/health/ready`, then configure and deploy Pages. `ENABLE_MODULES=learn,arcade,interview` after each service is configured. Set the frontend build variable `VITE_CORE_SOCKET_ORIGIN` to Core's HTTPS origin. Sockets connect directly to Core `/socket.io`, namespace `/core`; the Pages gateway handles HTTP APIs.
9. Copy `origins.example.json` to ignored `.local/deployment-origins.json` and record real assigned origins. Complete the hosted checks in `docs/learn-spike.md` before marking hosted PASS.

The user owns accounts, enters secrets and authorizes repository access; the assistant can prepare code/configuration, diagnose failures and verify assigned URLs. No passwords need to be shared in chat.

Render's workspace hours are shared across services. This design targets intermittent demos with sleep/cold starts, no keepalive jobs or paid fallback. Account eligibility, quotas and cold starts remain hosted checks. Official limits are in plan H1–H4.

References: [Render Blueprint](https://render.com/docs/blueprint-spec), [Render monorepos](https://render.com/docs/monorepo-support), [Pages routing](https://developers.cloudflare.com/pages/functions/routing/), [Pages build settings](https://developers.cloudflare.com/pages/configuration/build-configuration/).

## P7.1 Arcade setup

Create a separate logical Arcade Mongo database and an Arcade-only database user restricted to that database on the existing Atlas cluster. Put its URI only in Arcade's `ARCADE_MONGO_URI`. It must support transactions. Never reuse Core's database/user. The Render Arcade entry builds only its workspace/contracts and listens on Render's assigned PORT. It receives the Core public key, key ID, issuer `collegehubs-core`, audience `collegehubs-arcade`, public Core API base URL and matching APP_ORIGIN.

Provision a distinct Arcade service key with the existing stdin tool. Supply `service: "arcade"`, `keyId`, `key`, and `eventTypes: ["arcade.game_completed"]`. Learn has its own two event scopes listed above. Set the original Arcade key as its `CORE_SERVICE_KEY`. Generate another independent 32-byte base64url value (43 characters) for `ARCADE_RECONCILE_KEY`; it is only for direct service recovery, never browser/gateway configuration. Do not print keys or paste them in chat. Enable Arcade in Core and point Pages ARCADE_API_ORIGIN to its assigned HTTPS origin. Startup records the prospective NumberGuess Aura policy before accepting traffic.
